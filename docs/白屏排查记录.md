# 白屏排查记录

记录第二次真实问题的完整排查过程：**v1.0.1 装到手机上，能点开，但界面是一片空白，点什么都没反应。**

这一次比上次的「闪退」更难，因为**没有异常**。

---

## 现象

- v1.0.0：点开直接闪退（已修复，见 [闪退排查记录](闪退排查记录.md)）
- v1.0.1：能点开了，但界面是一片空白，没有任何文字，点哪里都没反应
- 手机：OPPO / vivo 系（ColorOS / OriginOS），Android 14

---

## 排查过程

### 第 1 步：先把「网页代码本身有问题」彻底排除

白屏的第一嫌疑永远是界面代码。所以先不猜，直接跑：

```bash
node tools/serve.js
```

用无头 Chrome 打开，把 DOM、控制台、截图全部抓下来。结果：

| 检查项 | 结果 |
| --- | --- |
| 页面标题 / readyState | 作业哨兵 / complete ✅ |
| 脚本是否执行 | `window.HWSentinelWeb` 存在 ✅ |
| 登录页渲染 | 可见，`display:grid`，高 820px ✅ |
| 登录后的主界面 | 5 张作业卡片全部渲染，无横向溢出 ✅ |
| JS 异常 | **0 条** ✅ |
| 控制台报错 | 0 条（只有一个 Chrome 自动请求 favicon 的 404）✅ |

结论：**网页代码在真实 Chromium 上是好的**，链路也对（`app/` 与
`assets/www/` 逐字节一致，APK 里的资源 SHA256 与源码完全相同）。

### 第 2 步：把所有「不抛异常也会白屏」的路径列出来

既然异常这条路已经堵上了（v1.0.1 加了自检 + 崩溃落盘），那就说明
**这次的失败根本没抛异常**。于是回头读 `MainActivity`，把所有
「WebView 什么都不说、只是显示空白」的情况列出来：

| 情况 | 老代码的行为 | 用户看到 |
| --- | --- | --- |
| `assets/www/index.html` 读不出来 | 没人检查 | **白屏** |
| 页面加载失败（`onReceivedError`） | 没有重写这个回调 | **白屏** |
| 渲染进程被杀（`onRenderProcessGone`） | 没有重写这个回调 | **白屏** |
| 页面加载很慢或卡住 | 没有任何提示 | **白屏，且不知道是在加载还是死了** |
| 网页脚本报错没跑起来 | 没人知道 | **白屏**（或一半界面） |
| 上一次崩溃过 | 错误页 + `return`，且崩溃文件**永不清除** | 每次打开都被挡住 |

**关键发现**：v1.0.1 只处理了「抛异常」，而上面这 6 种情况
**一个异常都不会抛**。`onPageFinished` 只能说明 HTML 下载完了，
它不知道脚本有没有跑起来、界面有没有真的画出来。

而白屏恰恰就藏在这条缝里。

### 第 3 步：复现——把「脚本没跑起来」真的做出来

要确认这就是白屏的成因，得让它真的发生。做法是复制一份 `app/`，
把 `app.js` 删掉，再用静态服务器打开（等价于安装包里这个文件读不到）：

```bash
node tools/blank-screen-test.mjs
```

修复前的表现符合预期：CSS 在、HTML 在，但脚本没跑，
界面停在初始状态——**用户看到的就是一片空白，没有任何解释**。

（顺便踩了一个坑：一开始想用 CDP 的请求拦截来模拟加载失败，
结果 Service Worker 和缓存把拦截绕过去了，测出来全是「假通过」。
换成真的删文件才可信。）

## 修复方案（v1.0.2）

核心原则一句话：

> **屏幕上任何时刻都必须有东西。**
> 要么是界面，要么是一段说明卡在哪一步的人话。

### 1. 网页层：启动占位层

`index.html` 里加一个 `#boot` 占位层（品牌色 + 转圈 + 「正在启动，请稍候…」），
由 `app.js` 在**确认界面真的画出来之后**才移除：

```js
var problem = interfaceIsVisible();
window.__HWS_READY__ = true;      // 就绪标记
if (problem) {
  // 占位层留着，把真实原因写在上面
  tip.textContent = '界面没能显示出来：' + problem;
} else {
  removeBootOverlay();           // 界面没问题才让它退场
}
```

另有 `<noscript>` 块兜住「JavaScript 完全没运行」的情况。

### 2. 网页层：自己检查界面到底画出来没有

```js
function interfaceIsVisible() {
  var shown = [].slice.call(document.querySelectorAll('.screen')).filter(s => !s.hidden);
  if (!shown.length) return '没有任何一个界面被显示';
  if (!shown.some(s => s.getBoundingClientRect().height > 40)) return '界面容器高度为 0';
  ...
}
```

### 3. 网页层：JS 错误会被记下来并交给原生层

在 `app.js` **最开头**挂上 `error` / `unhandledrejection` 监听，
把错误存进 `JS_ERRORS`，通过 `window.HWSentinel.reportProblem()` 告诉原生层。
原来的代码里没有这一段，脚本一报错，原生层完全不知情。

### 4. 安卓层：补齐所有「不抛异常」的回调

```java
onReceivedError           // 页面加载失败 → 说明原因
onReceivedHttpError       // 返回错误状态码 → 说明原因
onRenderProcessGone       // 渲染进程被杀 → 重建 WebView，而不是留一片空白
```

### 5. 安卓层：加载看门狗 + 页面自检探针

15 秒还没就绪，就往页面里注入一段说明（用 `transform` 挪到屏幕中间）：

```
已等待 30 秒，界面还没能显示出来。

网页层自检：{"readyState":"complete","hasAppJs":false,
"bootNode":true,"screenAuth":true,"localStorage":"ok"}

可以试着：① 重新打开应用；② 到应用商店更新「Android System WebView」；
③ 重启手机。若仍不行，请把这一屏截图发给开发者。
```

这些信息足够定位问题：`hasAppJs:false` 说明脚本没跑起来，
`readyState:"loading"` 说明卡在加载，等等。

### 6. 安卓层：资源包完整性自检

加载之前先把 `assets/www/index.html` 读一遍，读不到或内容不完整就直接报错，
**不去加载**——因为加载了也只会是白屏。

### 7. 安卓层：崩溃记录不再把应用永久卡死

老代码里 `last-crash.txt` 只有点「重新打开应用」才会清，
别的方式进来会一直看到错误页。现在**读过就删**，一个崩溃只展示一次。

### 8. 安卓层：远程调试

```java
WebView.setWebContentsDebuggingEnabled(true);
```

手机连电脑后 `chrome://inspect` 能直接看到这个页面，
白屏这类问题看一眼控制台往往就水落石出。

### 9. 顺手修掉的小问题

- CSS 的 `100dvh` 在 Chrome 108 以下不认，加了 `100vh` 兜底
- `file://` 来源下 `<link rel="manifest">` 必然被 CORS 拦，改成只在 http(s) 下挂
- 加了 `tools/check-android.ps1`：不用 Gradle 也能几秒钟确认安卓端编不编得过

## 经验总结

1. **「白屏」和「闪退」是两类问题，不能用同一套办法防。**
   闪退一定有异常；白屏往往**一个异常都没有**，代码里没人知道出事了。
   防闪退靠 try/catch，防白屏靠**主动确认界面到底画出来没有**。

2. **`onPageFinished` 不等于「界面能用了」。**
   它只说明 HTML 下载完了。脚本有没有跑起来、界面有没有渲染出来，
   它一概不知。必须让网页层自己回报一个「我真的起来了」的信号。

3. **界面上永远要留一个占位层。**
   加载中显示「正在启动」，失败就把它变成说明。
   「什么都不显示」是最坏的选择——用户不知道是在等还是已经死了，
   开发者也没有任何线索。

4. **加载失败的原因要由应用自己说出来。**
   这次加的自检探针（`readyState` / `hasAppJs` / `localStorage`）
   直接显示在屏幕上，用户截一张图就够定位，省掉一整轮来回。

5. **测试要测「真的故障」，不要测「模拟的故障」。**
   用请求拦截模拟加载失败时，Service Worker 把请求接走了，
   测出来全是假通过。删掉文件这种「真的坏掉」才可信。

6. **排查问题时先排除自己最熟的那一层。**
   这次先花了力气证明「网页代码没问题」——正因为排除了它，
   才把注意力转到安卓层，找到了那 6 条不抛异常的失败路径。
