# 闪退排查记录

记录一次真实问题的完整排查过程：**APK 装到手机上，点开直接闪退。**

---

## 现象

- 手机：OPPO / vivo 系（ColorOS / OriginOS），Android 14
- 安装方式：浏览器下载 APK 后点击安装，安装过程正常
- 打开后立刻闪退，看不到任何界面，也没有报错提示
- v1.0.0（versionCode 1）必现

---

## 排查过程

### 第 1 步：先排除「包本身有问题」

用 `aapt2` 检查 APK，确认包结构没问题：

```bash
aapt2 dump badging app-release.apk
aapt2 dump xmltree --file AndroidManifest.xml app-release.apk
apksigner verify --verbose app-release.apk
```

结论：

| 检查项 | 结果 |
| --- | --- |
| 包名 / 版本 | `com.homesentinel.app`，versionCode 1，versionName 1.0.0 |
| minSdk / targetSdk | 24 / 34 ✅ |
| application / activity / receiver | 全部正确注册，`exported` 无误 ✅ |
| 权限 | POST_NOTIFICATIONS、SCHEDULE_EXACT_ALARM 等齐全 ✅ |
| 签名 | v2 方案验证通过 ✅ |
| 网页资源 | `assets/www/` 下 8 个文件都在 ✅ |

**包本身没问题**，所以是启动时的运行时异常。

### 第 2 步：复查启动代码

v1.0.0 的 `MainActivity.onCreate()` 是这样写的：

```java
web = new WebView(this);          // ← 没有任何保护
root.addView(web);
setContentView(root);
configureWebView();
web.loadUrl("file:///android_asset/www/index.html");
```

这段代码**没有任何异常保护**。只要其中任何一步抛异常，进程就直接崩溃，
用户看到的就是「点开闪退」，而且完全不知道原因。

### 第 3 步：锁定最可能的原因

在国产 ROM 上，**「Android System WebView」组件可能被精简、禁用或被替换成不完整的内核**。
这时 `new WebView(this)` 会直接抛异常。

这个假设同时解释了三个现象：

1. 安装正常（安装阶段不碰 WebView）
2. 点开立刻闪退（`onCreate` 里第一步就崩）
3. 用户是国产 ROM + 较新系统（WebView 被管控的高发环境）

其他被逐一排除的可能：主题解析失败、图标资源缺失、权限申请崩溃、
`SharedPreferences` 初始化失败（见上面第 1 步的资源与清单检查）。

### 第 4 步：尝试真机复现（未成功）

想用安卓模拟器复现并抓 logcat，但：

- 模拟器需要硬件加速（AEHD 驱动或 Windows Hypervisor Platform），
  两者都需要管理员权限，当前环境拿不到
- 不加速时 x86_64 镜像启动失败（`Failed to proc`）
- 系统镜像 + 模拟器占 5.3 GB，最终放弃这条路

**结论：在这个环境里无法复现，改为让应用自己把崩溃原因说出来。**

---

## 修复方案（v1.0.1）

既然没法在本地复现，就**让应用在用户的手机上自己完成诊断**。

### 1. 启动前自检

用 `WebView.getCurrentWebViewPackage()`（API 26+）检查系统 WebView 是否可用，
不可用就直接给出明确结论和恢复办法：

```java
android.content.pm.PackageInfo pi = WebView.getCurrentWebViewPackage();
if (pi == null) {
    return "系统里没有找到可用的 WebView 组件。";
}
```

### 2. 启动全程异常保护

每一步单独兜住异常，任何一步失败都显示可读的错误页，而不是闪退：

```java
try {
    buildUi();
} catch (Throwable t) {
    showCrashScreen(t);
    return;
}
```

`buildUi()` 内部再细分：建 `WebView`、配置 `WebSettings`、加载页面、
申请通知权限，各自独立 try/catch —— 这样即使通知权限申请失败，
界面照样能用（这是「非致命」和「致命」的区分）。

### 3. 崩溃落盘，下次打开时展示

这里有个容易踩的坑：**未捕获异常发生后如果调用系统默认处理器，进程会被杀掉**，
`runOnUiThread` 排队绘制的错误页根本来不及显示；如果是子线程崩溃，
情况更糟。

所以改成：**先把崩溃信息写进文件**，下次启动时读出来展示。

```java
// 崩溃时
FileOutputStream fos = openFileOutput("last-crash.txt", MODE_PRIVATE);
fos.write(detail.getBytes("UTF-8"));
fos.close();

// 主线程崩溃：自己画错误页，且不把异常交回系统（否则进程立刻被杀）
if (thread == Looper.getMainLooper().getThread()) {
    showCrashScreen(error, detail);
    return;
}
// 子线程崩溃：进程还活着，下次进前台再展示
```

### 4. 错误页要能直接拿来定位

错误页包含：

- 手机型号、系统版本、API 级别
- 应用版本号
- **系统 WebView 的版本号**（关键信息，一眼看出是不是这的问题）
- 完整异常堆栈

并提供两个按钮：

- **重新打开应用** —— 清掉崩溃记录，重新搭建界面
- **复制错误信息** —— 一键复制到剪贴板，粘到聊天里就能发出去

### 5. 错误页给的是「能操作的办法」

按成功率排序：

1. 到应用商店搜索并更新「Android System WebView」和「Chrome」
2. 设置 → 应用管理 → 显示系统程序 → Android System WebView → 启用
3. 设置 → 应用管理 → 作业哨兵 → 清除数据后重新打开
4. 重启手机后再试

## 用 adb 抓崩溃日志（最终手段）

如果错误页也没出现，说明连错误页都没能画出来。这时用 adb 抓日志：

1. 手机：设置 → 关于手机 → 连续点「版本号」7 次，开启开发者选项
2. 设置 → 开发者选项 → 打开「USB 调试」
3. 用数据线连电脑，手机上允许调试
4. 电脑上执行：

```bash
adb logcat -c                                    # 先清空
adb logcat | grep -E "AndroidRuntime|homesentinel"
# 然后在手机上打开应用，崩溃信息就会打印出来
```

重点看这两行：

```
FATAL EXCEPTION: main
Caused by: ...
```

`Caused by` 后面就是根本原因。

也可以直接导出完整日志：

```bash
adb logcat -d > crash.log
```

---

## 经验总结

1. **「点开就闪退」= `onCreate` 里抛了未捕获异常**，不要怀疑安装包本身，
   先用 `aapt2` + `apksigner` 排除包结构问题，然后直查启动代码。
2. **界面依赖系统组件的应用，必须假设该组件可能不存在**。
   WebView 是最典型的例子，国产 ROM 上被精简/禁用并不罕见。
3. **不要依赖「崩溃时弹个界面」**。进程会被杀掉，界面来不及画。
   落盘 + 下次启动展示，才是可靠做法。
4. **错误信息要包含环境和版本**。这次错误页里带上了 WebView 版本号，
   用户一截图就能确认是不是 WebView 的问题，省掉一轮来回。
5. **给用户的恢复步骤要按成功率排序**，并且是他自己能操作的。
